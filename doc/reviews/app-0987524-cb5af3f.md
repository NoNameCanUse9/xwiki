## 1. [高] 文件历史功能回归

### 现象
文档历史面板（从编辑器"历史"入口打开）实际显示**整个项目的提交**，而非当前文件的历史；搜索和"加载更多"同样混入无关文件。

### 证据：回归发生在范围内
`7fec4bc`（paginate history and select token projects）把加载逻辑从文件级 API 换成了项目级 API：

- **7fec4bc 之前**（src/app/mod.rs:1677-1688）：
  ```rust
  fn load_file_history(&mut self, cx: &mut Context<Self>) {
      ...
      async move |this, cx| match client.file_history(&project, &path).await { ... }
  ```
  调用文件级接口 `/api/v1/projects/{id}/files/history/{path}`。

- **7fec4bc 之后（当前 cb5af3f）**（src/app/mod.rs:1749-1750 → 1800-1831）：
  ```rust
  fn load_file_history(&mut self, cx: &mut Context<Self>) {
      self.load_history_page(true, cx);
  }
  ...
  fn load_history_page(&mut self, reset: bool, cx: &mut Context<Self>) {
      let (Some(client), Some(project), Some(path)) = (... history_file_path.clone() ...) else { return; };
      ...
      client.commits_search_page(&project, &query, HISTORY_PAGE_SIZE, offset).await
  ```
  `path` 被解构出来但**从未传给 API**；`commits_search_page`（src/api/mod.rs:542-560）请求 `/api/v1/projects/{id}/commits?q=&limit=&offset=`，纯项目级。

- **死代码**：文件级 `client.file_history(project_id, path)`（src/api/mod.rs:767-777，请求 `/files/history/{path}`）**无任何调用者**（编译器 dead-code 警告属实）。

- **需求依据**：`spec.md:56` 明确要求"提交列表、提交详情、numstat/patch Diff、**文件历史**、历史版本预览、恢复版本和 Revert"。

### 修复建议
`load_history_page` 按 `history_file_path` 走 `file_history` 接口：
- 简单方案：有文件路径时调 `file_history`（无分页的旧接口），无路径（项目级场景）才走 `commits_search_page`；
- 完整方案：给 `file_history` 接口补 `q/limit/offset` 参数支持分页与搜索，前端统一走它。

## 2. [高] contract CI checkout 布局错误

### 现象
契约作业（用 main 服务端跑 app 的 e2e_contracts）**从创建起就跑不通**——第二次 checkout 会清掉第一次 checkout 的内容。

### 证据
app 分支 `.github/workflows/ci.yml`（当前 cb5af3f，含改名回滚后）contract job：

```yaml
- uses: actions/checkout@v4
  with: { path: server, ref: main }   # ① main → server/
- uses: actions/checkout@v4            # ② app → 工作区根（无 path）
...
- name: Build server
  run: go build -o xwiki ./cmd/xwiki
  working-directory: server            # ③ 此时 server/ 已被 ② 清掉
```

`actions/checkout@v4` 默认 `clean: true`，② 在 checkout 前对工作区根执行 `git clean -ffdx`——`server/` 是未跟踪目录，**必然被删除**。③ 及后续 `working-directory: server` 步骤必失败。这是 checkout action 的已知行为，非推测。

### 对照：main 分支有正确样板
main 分支 `.github/workflows/ci.yml` 的 contract job 是标准双路径布局：

```yaml
- uses: actions/checkout@v4
  with: { path: server, ref: main }
- uses: actions/checkout@v4
  with: { path: app, ref: app }
...
- name: Run cross-branch contract tests
  working-directory: app
  run: cargo test e2e_contracts -- --ignored
```

app 分支抄漏了 `path: app` 与 `working-directory: app`。

### 复核修正（词性）
该 job 由 `0987524` 新增（`0987524^` 的 ci.yml 无 contract job），所以是**新增功能从未跑通**，而非既有功能的回归。审查者"破坏 0987524 的目标"的定性正确。

### 联动影响
契约测试（`cargo test --locked e2e_contracts -- --ignored` + `XWIKI_TEST_SERVER`）因此**从未在 CI 上执行过**，包括 #3 涉及的 token 权限测试。

### 修复建议
照抄 main 样板：② 加 `with: { path: app, ref: app }`，契约测试步骤加 `working-directory: app`。一行配置，优先修。

## 3. [中] token 权限测试假阳性

### 现象
只读 token 的"只能看到绑定项目"断言在 API 返回空列表时也会通过。

### 证据
src/api/e2e_test.rs:174-179：

```rust
let ro = Client::with_token(&server, Some(secret.clone()));
let visible = ro.projects().await.expect("ro project list");
assert!(
    visible.iter().all(|p| p.id == pid),
    "read token must only see its bound project"
);
```

- 空列表时 `iter().all(...)` 返回 `true`——若权限过滤 bug 导致 token 一个项目都看不到，测试仍绿；
- 断言只覆盖"看不到外来项目"，不覆盖"**看得到自己绑定的项目**"（正向断言缺失）。

### 复核修正（影响面）
- 该测试属于契约测试（`--ignored` + `XWIKI_TEST_SERVER`），因 #2 的 CI 布局问题**从未运行过**，假阳性目前无实际危害，但一旦 #2 修复、契约测试上线，此断言即成为漏洞。
- 测试内其他断言（`apply_changeset` 403 等）是正常的，仅 projects() 列表这条偏弱。

### 修复建议
```rust
assert!(visible.iter().any(|p| p.id == pid), "bound project visible");
assert!(visible.iter().all(|p| p.id == pid), "no foreign project visible");
```
更严格：用 ro 客户端读该项目的页面/文档，验证确实可读。

## 4. [中] Git 依赖未按 spec 固定 rev

### 现象
`Cargo.toml` 中 GPUI / gpui-component 为无 `rev` 的浮动 Git 依赖，违反 `spec.md` 的固定要求。

### 证据
- `spec.md:24`：`将 GPUI、gpui-component 固定到验证过的兼容 commit，并提交 Cargo.lock。GPUI 仍处于 pre-1.0，不能继续使用浮动 Git HEAD 依赖。`
- app 分支 `Cargo.toml:7-8`（注释）：
  ```
  # All zed crates unpinned so cargo resolves a single gpui for us and for
  # gpui-component (which also depends on zed main). Reproducibility comes from Cargo.lock
  ```
- `Cargo.toml:10`：`gpui = { git = "https://github.com/zed-industries/zed.git" }`（无 rev）
- `Cargo.toml:17`：`gpui-component = { git = "https://github.com/longbridge/gpui-component" }`（无 rev）
- `Cargo.lock` 已提交，`--locked` CI 下可复现构建。

### 复核修正（定性）
**这不是无意的漂移，而是 spec 与实现的有意冲突**：Cargo.toml 注释明确声明"unpinned 是设计选择，可复现性交给 Cargo.lock"，且锁文件已提交。审查者的事实描述（无 rev、靠 lock 固定）准确，但"只靠 Cargo.lock 固定"正是当前实现的声明意图。

风险依然成立：任何执行 `cargo update`（或删除 lock 重新解析）都会漂移到最新 zed main，可能引入 pre-1.0 破坏性变更。`--locked` CI 只能防漂移，不能防首次解析。

### 修复建议
二选一并同步更新另一边：
1. 按 spec 补 `rev` 固定（推荐，spec 意图明确）；
2. 若坚持 unpinned 策略，更新 `spec.md:24` 以反映现状（spec 与实现必须一致）。
